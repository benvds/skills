# Outline

This file covers Phase 5. The user writes the outline; you give feedback; the user refines. The loop repeats until the user says the outline is good enough. No paragraphs are written in this phase. An outline here is a skeleton of claims: headings, and for each paragraph one core sentence. Someone who reads only the core sentences should be able to follow the argument.

## Ask for the outline

Ask the user to write, per section:

- a heading that says what is in it ("What it costs", not "The road ahead");
- per paragraph, one core sentence that states a claim, not a topic ("Headings help readers remember", not "About headings");
- per paragraph, a word target from the budget (see `budget.md`).

With a budget, say before the user starts how many paragraphs fit, as a range. With a time budget, do the reality check from `budget.md` first.

Give the sub-questions from Phase 3 as the starting order. For a report, each sub-question usually becomes a section. For an article, the reader's questions become the sections.

If the user prefers to start by writing freely, that is fine. Then make a reverse outline of what they wrote (see `drafting.md`) and use it as their first attempt.

## Structures to offer

Offer one of these when the user asks, or when the order doesn't work. Explain each in one line.

**Report.** Answer first: the main conclusion or advice on top, then the sections that support it, each with its own conclusion first (the pyramid principle). Then method or approach, limits, and appendices. A board reader may read only the first page; that page must contain the answer.

**Informative article.** Point in the first paragraph. Then the reader's questions in their order: why it matters, how it works, what it means for the reader, what we don't know yet.

**Opinion piece.** Opening with a situation the reader recognises and the stance within a few sentences. Then the reasons with evidence, the strongest objection stated fairly, the answer to it, and what changes if the stance is right.

## The loop

1. The user writes an attempt at the outline, or a revised version.
2. You check it against the list below and give feedback as in **How you give feedback** in `SKILL.md`: at most three points, ending with one next step.
3. The user refines. Then back to step 2.

The loop ends when the user says the outline is good enough. In each round, say which earlier points are now solved. If the user is stuck on one part, offer two or three options for that part only. Never write the whole outline.

## Check the outline

Read `craft.md` first. Then check:

1. **Point.** Does every paragraph serve the point? A paragraph that doesn't, goes, even if it is good.
2. **Core sentences.** Read only the core sentences. Do they form the argument? Is each one a claim?
3. **Order.** Does each section answer the question the reader has at that moment? Does the answer come early enough for this reader?
4. **Evidence.** Is every claim that needs support linked to a source card or to the user's own example? For an opinion piece: is the type of evidence right for the reader? Numbers work better when the reader is not personally involved; a case works better when the reader is involved, or when the goal is that they act.
5. **Objection.** Opinion piece: is the strongest objection named fairly and answered? An objection that is mentioned but not answered weakens the piece.
6. **Budget.** Does the number of paragraphs fit the budget, and do the word targets add up to it within 10%? A rough guide: 100 to 150 words per paragraph. With a time budget: does the outline hold only what is on "fits"?
7. **Gaps and research.** Do research findings that challenge the point have a place, or has the point been narrowed?

## Save the outline

Save the outline in the status file in this form:

```
- [stated] 2.1 · core: Teams that write first decide faster · ~120 w · status: open · sources: R1, R4
```

Statuses per paragraph: `open`, `attempt` (the user wrote a version), `feedback` (you gave feedback on the latest version), `done` (the user says it is good enough). Note `proposal` when the user asked for one.

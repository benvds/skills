# Budget: words or time

This file covers the budget question in Phase 1 and what the budget changes later. A budget is the size of the text in words, the time the user has for it, or both. It sets how many sub-questions fit, how many paragraphs the outline gets and how long each one is.

## Ask it in the intake

Ask before any other work starts, as one of the intake questions:

- **Words:** the length of the text, such as "about 1,200 words" or the limit of the channel.
- **Time:** the hours the user will spend on the text in total, until the deadline.
- **Both:** a length and the time to write it.
- **No budget:** the length follows from the channel, and there is no planning.

If the user already named a budget, such as "max 800 words" or "I have three evenings", ask only what is still open. For a word budget, ask whether it is a hard limit (a magazine, an assignment) or a target. For a time budget, ask how many sessions that is and how long each one is.

## Word budget

The word budget shapes the outline.

1. **Split it.** Reserve about 10% for the opening and 10% for the close. The rest is the body. These shares are a practice rule, not a research finding.
2. **Count paragraphs.** A paragraph is about 100 to 150 words. Divide the body by that, and give the result as a range: 1,000 body words is 7 to 10 paragraphs.
3. **Check the sub-questions.** A section needs at least two paragraphs to make a claim and support it. So the number of sections that fit is about half the number of paragraphs. If there are more sub-questions than fit, say so in Phase 3 and let the user choose: merge two, drop one, or narrow the point. For an opinion piece, the strongest objection keeps its section.
4. **Give every paragraph a target.** In the outline, each paragraph gets a word target, such as `~120 w`. Start with an even split and let the user give more words to the section that carries the point. The targets add up to the budget, within 10%.

While the user writes, give the word count next to the target in the feedback. Mention it only when a section runs more than 25% over, or when the total will clearly not fit. A paragraph under its target is fine if it makes its claim. Don't ask the user to pad.

At the polish, report the total against the budget. If a hard limit is exceeded, list cuts that cost the point least, and let the user choose. Don't cut yourself.

## Time budget

No research says how long a paragraph of an article takes to write. What is well researched is that people underestimate how long tasks take, and what helps against it: splitting the work, a range instead of one number, planning back from the deadline, and measuring instead of remembering. The method follows that (see choice 12 in `DESIGN.md`).

1. **Split.** Estimate the steps one by one: point and sub-questions, the outline loop, each paragraph with its feedback rounds, the reverse outline, the polish and content check, and the reader test. Research runs in the background; count only the time to read the summaries.
2. **A range.** Ask the user how long a paragraph usually takes them. If they don't know, plan with 20 to 45 minutes per paragraph, including two feedback rounds, and say that this is a starting guess, not a measurement.
3. **Plan back from the deadline.** What must be done in the last session, and in the one before? Planning from the end back to now gives more realistic estimates than planning forwards.
4. **Reality check, together.** Show it:

```
Time budget:      [T] hours until [deadline], in [n] sessions
Fixed steps:      [f] hours (point, sub-questions, outline, polish, content check, reader test)
For paragraphs:   [T − f] hours
Per paragraph:    [low] to [high] min (starting guess; measured after 3 paragraphs)
Fits:             [p_low] to [p_high] paragraphs, about [w_low] to [w_high] words
```

Plan with the high end. Then make three lists, in terms of sub-questions or sections:

- **Fits:** what can be written even at the high estimate.
- **Almost fits:** what can be added if the pace turns out better.
- **Out of reach:** what doesn't fit in this budget.

The user chooses: narrow the point, drop a sub-question, write a shorter text, or find more time. The outline then gets only what fits. If the user also gave a word budget, check whether it fits the time. If it doesn't, the user chooses which one gives way.

## Measure along the way

- **Measure, don't remember.** At the end of each session, ask how long the user worked on the text, and note it in the log with the paragraphs that changed status. People underestimate afterwards how long something took, so ask right away, not a week later.
- **After three paragraphs**, divide the measured minutes by the paragraphs that are `done`. That replaces the starting guess. Put it in the status file.
- **Project the end.** With the measured pace, do the remaining paragraphs fit before the deadline? If not, redo the reality check with the user. Say so too when things go faster than planned, and offer what was on "almost fits".

## A small budget

With a small time budget, such as one or two hours, or a text under 600 words:

- Combine the point and the sub-questions in one round.
- Start one research agent for all sub-questions, and give it a tighter brief: one or two sources per sub-question.
- Ask once whether the user wants options straight away instead of trying first (see choice 2 in `DESIGN.md`). Save the answer as a decision.
- Suggest stopping each paragraph after two feedback rounds. The user still decides when a paragraph is good enough.

## Save the budget

Save the budget in the status file under **Budget**, and the word target per paragraph in the outline lines (see `storage.md`). When the budget changes, update the outline targets and the reality check, and note the change under **Decisions**.
